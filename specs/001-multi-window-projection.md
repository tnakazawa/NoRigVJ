# 001: マルチウィンドウ構成(操作UI / 投影窓)

- ステータス: Implemented
- 作成日: 2026-09-11

## 背景・目的

現状は1つのウィンドウにcanvasとHUDが同居しており、投影(観客が見る画面)と操作(VJ本人が操作する画面)が分離できていない。同一PCで外部ディスプレイ/プロジェクタに投影しつつ、手元のノートPC画面では操作パネルを見ながら操作できるようにする。

## 要件

- 操作UI(Control Window)と投影窓(Display Window)を分離した2ウィンドウ構成にする。
- **マイク入力・音声解析は操作UI側で行う。** 投影窓はマイク権限を持たない。
- 操作UIの「投影窓を開く」ボタンから `window.open()` で投影窓を新規ウィンドウとして開く。
- ウィンドウ間の状態同期は **BroadcastChannel API** で行う。操作UI側がrAFループ内で毎フレーム `{ sceneIndex, intensity, audioLevels, time }` をブロードキャストし、投影窓はそれを受信して描画する。操作UI側が状態のsingle source of truthであり、投影窓は状態を保持しないステートレスなレンダラーとする。
- 投影窓は受信した最新状態を使い、`scenes.ts` の既存レンダリングロジックをそのまま利用してフルスクリーン背景に描画する。UIやHUDは表示しない。
- 操作UI側にも同じシーンを描画する小さなプレビューcanvasを表示する(投影窓を見なくても仕上がりを確認できる)。
- 操作UIは既存のキーボード操作(1〜3でシーン切替、←/→で強度調整、Spaceでマイク有効化)を維持しつつ、同等の操作ができるGUI(シーン選択ボタン、強度スライダー、マイクON/OFFボタン)を追加する。
- 投影窓は `F` キーでFullscreen APIによるフルスクリーン切り替えに対応する。
- 操作UIは投影窓の接続状態(接続中/未接続)をHUDまたはUI上に表示する。
- 投影窓を閉じて再度開いた場合、操作UI側は状態を保持し続けているため、再接続後は自動的に現在のシーン・強度が反映される(特別な状態保存/復元処理は投影窓側に持たせない)。

## 非機能要件

- 引き続きオフラインで動作すること(外部リクエスト不要)。
- 特別なオーディオインターフェース・MIDI機材を必要としないこと。
- BroadcastChannelは同一オリジンの複数タブ/ウィンドウ間でのみ動作するため、操作PCと投影PCが物理的に別端末になるケースは本仕様のスコープ外(将来の拡張候補として `specs/README.md` の対象外扱いにする)。

## 受け入れ基準

- [ ] 操作UIの「投影窓を開く」ボタンで新規ウィンドウが開き、フルスクリーン背景として描画される
- [ ] 操作UIでシーン切替・強度調整・マイクON/OFFをGUI操作すると、投影窓の描画にリアルタイムに反映される
- [ ] 操作UI側にも同じビジュアルの小さなプレビューが表示される
- [ ] 投影窓上で `F` キーを押すとフルスクリーン⇔通常表示を切り替えられる
- [ ] 投影窓を閉じても操作UIはエラーなく動作を続け、「投影窓: 未接続」がわかる表示になる
- [ ] 未接続状態から投影窓を再度開くと、操作UI側の現在のシーン・強度がすぐに反映される
- [ ] 既存のキーボード操作(1〜3 / ←→ / Space)は操作UI上で引き続き動作する

## 実装メモ

- Viteのマルチページ構成(`control.html` + `display.html`、それぞれ `src/control.ts` / `src/display.ts` を持つ)を想定。`src/scenes.ts` と `src/audio.ts` は両エントリから共有する。
- 投影窓が開いているかどうかの判定は、`window.open()` の戻り値(`WindowProxy`)の `closed` プロパティを操作UI側でrAFループ内でポーリングする方式を採用した。
- BroadcastChannelでの状態同期・シーン切替は実機ブラウザ(開発サーバー上の2タブ)で動作確認済み。`F` キーによるFullscreen APIは検証に使ったBrowser Pane環境がPermissions Policyでブロックしていたため確認できていない。実際のデスクトップブラウザ(Chrome等)で改めて確認すること。
- 1画面PCで投影窓をフルスクリーン化すると操作窓が完全に隠れ(occluded)、Chromeが操作窓の `requestAnimationFrame` を強くスロットルして音声解析・状態送信が止まる問題を確認。対策として `src/control.ts` の音声解析・状態計算・BroadcastChannel送信は `setInterval`(33ms)で回し、rAFはプレビュー描画のみに使うよう分離した。
- 上記の `setInterval` だけでも、occludedウィンドウではChromeがタイマーを最小1秒間隔にクランプするため状態更新がカクついた。Worker内のタイマーはこの抑制を受けないため、`src/tick-worker.ts` を追加し、tickを駆動するタイミングだけWorkerからの `postMessage` に任せる方式に変更した(音声解析自体はメインスレッド側で行う。`getUserMedia`/`AnalyserNode` はWorkerから直接扱えないため)。

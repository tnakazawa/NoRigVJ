# 006: シーン間クロスフェード

- ステータス: Implemented
- 作成日: 2026-09-14

## 背景・目的

現状、投影窓のシーン切替は即座に切り替わる。VJ現場では、シーン間を滑らかに(数百ms〜数秒かけて)遷移させたい場面がある。投影窓ごとに「クロスフェード実行」を手動トリガーできるようにする。

## 要件

### UIモデル: 予約 → 実行の二段階

投影窓行のシーン選択・カラーパレット設定・プリセット選択は、すべて **「次に切り替える内容(予約)」を編集するもの** に統一する。実際の反映(=現在の表示の切り替え)は「クロスフェード実行」ボタンを押すまで起きない。

- **現在の状態**(`sceneIndex` / `palette`) — 実際にプレビュー・投影窓に描画されている内容。
- **予約状態**(`pendingSceneIndex` / `pendingPalette`) — シーン選択セレクトボックス・パレットのプリセット選択・カラーピッカー・シーンプリセット選択、これら全てが編集する対象。投影窓追加直後・クロスフェード完了直後は、予約状態を現在の状態と同じ値で初期化する。
- **「クロスフェード実行」ボタン** — 現在の状態から予約状態へ、指定時間(下記)かけて遷移する。予約状態が現在の状態と完全に一致する(シーン・パレットとも同じ)間はボタンを無効化する。
- シーンプリセットの呼び出しも「予約状態への反映」として扱う(プリセットを選ぶと予約のシーン・パレットが変わるだけで、クロスフェード実行ボタンを押すまで表示には反映されない)。
- 操作UIの各投影窓行には、「現在」のプレビューの隣に「次へ(予約)」のプレビューも常時表示する。予約内容を変更すると、このプレビューにすぐ反映される(実際に動いている見た目を確認できる)。

### クロスフェード時間

- 操作UIのパネルに、全投影窓共通のクロスフェード時間スライダーを1つ用意する(強度スライダーと同様の位置づけ)。

### 実装方式: CSS opacityトランジションによるレイヤー合成

- 自前でピクセル単位の合成計算(2Dの`drawImage`によるアルファブレンド等)は行わない。クロスフェード実行時、予約シーン用の一時レイヤー(2DまたはWebGL、シーンの`kind`に応じたcanvas要素)を現在のレイヤーに重ねてDOMに追加し、`opacity: 0 → 1` のCSSトランジションで見た目のブレンドをブラウザのコンポジタに任せる。
- クロスフェード中は、現在のシーン(旧レイヤー)・予約シーン(新レイヤー)の両方を毎フレームレンダリングし続ける(この間だけ2シーン分の描画負荷がかかるのは許容する)。
- トランジション完了後、旧レイヤーの canvas要素とシーンインスタンスを破棄する。新レイヤーが以後の「現在のレイヤー」になる。
- この処理は操作UIのプレビューと投影窓の両方で行う(投影窓側は別プロセス相当のウィンドウなので、それぞれ独立してレイヤー管理・CSSトランジションを実行する)。

### BroadcastChannelでの伝搬

- 投影窓にもクロスフェードを実行させるため、`VJState` に `crossfadeByWindow: Record<windowId, CrossfadeInstruction | null>` を追加する。`CrossfadeInstruction` は少なくとも「遷移先のシーン名・パレット」「クロスフェード時間」「開始を示す情報」を含む。
- 投影窓側は、操作UIとは独立して自分自身のタイミングでレイヤー追加・CSSトランジション・完了後のレイヤー破棄を行う(操作UI側から都度「進捗%」を送るのではなく、開始トリガーと時間だけを伝え、各ウィンドウが自律的にトランジションを実行する)。

## 非機能要件

- クロスフェードを使わない既存の運用(即座切替相当の操作性)も引き続き成立すること。ただし今回の変更でシーン選択自体は「予約→実行」の二段階に統一されるため、操作感は変わる。
- 既存の複数投影窓・カラーパレット・シーンプリセット・マルチウィンドウ機能は引き続き問題なく動作すること。

## 受け入れ基準

- [x] シーン選択・パレット設定・プリセット選択は、選んだだけでは表示に反映されず「予約」として保持される
- [x] 「クロスフェード実行」ボタンを押すと、現在のシーンから予約シーンへ、指定時間かけて滑らかに遷移する(操作UIのプレビュー・投影窓の両方で)
- [x] 予約状態が現在の状態と同じ場合、「クロスフェード実行」ボタンは無効化される
- [x] クロスフェード時間はパネルの共通スライダーで調整できる
- [x] クロスフェード完了後、旧シーンのレイヤー・インスタンスは破棄され、通常時と同じ「1シーンのみレンダリング」の状態に戻る
- [x] シーンプリセットを呼び出すと予約状態が更新され、クロスフェード実行ボタンで反映できる
- [x] 各投影窓行に「現在」「次へ(予約)」のプレビューが並んで常時表示され、予約を変更するとすぐに「次へ」側のプレビューへ反映される
- [x] 既存の複数投影窓・カラーパレット・BroadcastChannel同期・フルスクリーンなどは引き続き問題なく動作する

## 実装メモ

- [src/layer.ts](../src/layer.ts) に `Layer`(1シーン分のcanvas2枚・専用`WebGLRenderer`・シーンインスタンス一式)という共通概念を導入し、control.ts・display.tsの両方がこれを使う設計に統一した。**シーン切替は(クロスフェードの有無を問わず)常に新しいレイヤー = 新しいシーンインスタンスを生成する**方式に変更している。理由: クロスフェード中は旧シーン用・新シーン用で別々のcanvas/`WebGLRenderer`が必要になるが、three.jsの`WebGLRenderTarget`は特定のrendererに紐づくため、「投影窓ごとに全シーンを事前生成して使い回す」という旧設計([specs/002-webgl-scenes.md](002-webgl-scenes.md)・[specs/003-multiple-display-windows.md](003-multiple-display-windows.md)時点の設計)とは両立しなかった。トレードオフとして、Feedback Loopのような蓄積系シーンの状態はシーンを切り替えるたびにリセットされるようになった(この変更はユーザーに確認の上で合意済み)。
- [src/crossfade.ts](../src/crossfade.ts) の `startCrossfade()` が実際のトランジション制御(DOM追加・`opacity`のCSSトランジション・`setTimeout`での完了検知・旧レイヤー破棄)を担う。自前のピクセル合成コードは書いていない。
- `VJState.crossfadeByWindow` に `CrossfadeInstruction { id, toSceneName, toPalette, durationMs }` を持たせ、`id`(`crypto.randomUUID()`)で「新規のクロスフェード発生」を判定する。投影窓側は毎tick同じ`id`を受け取っても再度開始しない。
- シーン名からインデックスを引く必要がある箇所(プリセット呼び出し、クロスフェード先の解決)のため、[src/scenes/index.ts](../src/scenes/index.ts) に `sceneNames: string[]` を追加した(起動時に各シーンを1回だけ使い捨てインスタンス化して `name` を読む)。
- 「次へ」プレビュー用に、`DisplayEntry.pendingLayer` を常時1つ保持し、常時レンダリングし続ける設計にした(操作UI側のみ。投影窓は実際に映す1シーンしかレンダリングしない)。この `pendingLayer` はクロスフェード実行時にそのまま遷移先レイヤーとして使う — つまり「予約プレビュー用レイヤー」と「クロスフェードのtoレイヤー」を同一インスタンスに統合している。クロスフェード開始と同時に、今回の遷移先と同じ内容の新しい `pendingLayer` を先に用意しておくことで、「次へ」プレビュー欄がクロスフェード中に空白にならないようにしている。トレードオフ: 操作UI側は常に「現在+予約」の2レイヤー分のレンダリングコストがかかる(投影窓側は変わらず、実際にクロスフェードする瞬間だけ2レイヤーになる)。
- 実機Chrome(開発サーバー、`window.open` を一時的にスタブ化してこの環境の制約を回避しつつ)で、予約→実行の二段階UI・「次へ」プレビューの即時反映とクロスフェード中の維持・クロスフェード中のopacityブレンド・完了後のレイヤー破棄と次の予約レイヤーの用意・複数投影窓での独立したクロスフェード・BroadcastChannel経由での投影窓側への反映・プリセット呼び出しからのクロスフェードを確認済み。
- 本文中の「クロスフェード実行」「現在」「次へ」などのラベルは要件定義当時の日本語表記。UIは後日英語化されており、実際のラベルは「Crossfade」「Current」「Next」(それぞれ [control.ts](../src/control.ts) 参照)。
- バグ修正: Crossfade duration(`durationMs`)が0のとき、投影窓側にクロスフェードが一切反映されないバグがあった。
  - 1回目の修正(不十分だった): `toLayer`のopacityを`0→1`にする処理が2重`requestAnimationFrame`(次フレーム以降に実行)を経由するのに対し、完了処理(`disposeLayer`・`onComplete`)は`setTimeout(fn, durationMs)`で予約しており、`durationMs=0`だと`setTimeout(fn, 0)`の方が2重rAFより先に発火することがあるレースコンディションを見つけ、`durationMs <= 0`の場合に`opacity:1`・`dispose`・`onComplete`を全て同期的にその場で呼ぶよう変更した。これでcontrol.ts内のプレビュー(`currentLayer`)は正しく切り替わったが、実際の投影窓では相変わらず切り替わらないと指摘を受けた。
  - 真因: `control.ts`の`startEntryCrossfade()`は、クロスフェード実行中だけ`entry.crossfadingInstructionId`をセットし、`tick()`(`TICK_INTERVAL_MS`=33ms間隔、[tick-worker.ts](../src/tick-worker.ts)参照)が`crossfadeByWindow[windowId]`としてBroadcastChannel経由で投影窓に送信する。1回目の修正で完了処理まで同期的に呼んでしまうと、`entry.crossfadingInstructionId`がセットされている時間が実質0(1回の関数呼び出し内)になり、次の`tick()`が発火する前に`null`へ戻ってしまう。結果、`crossfadeByWindow`に一度もこの指示が乗らないまま完了し、投影窓には「切り替えろ」という指示自体が届かなかった(操作UI側のプレビューは`entry.currentLayer`を直接書き換えるコールバックなので、同期処理でも正しく見えてしまい、テスト時に見逃す原因になった)。テスト用に`BroadcastChannel`の受信側を直接フックして`crossfadeByWindow`の送信回数を計測し、この原因を特定した。
  - 修正: `durationMs <= 0`の場合、見た目は即座に`opacity:1`にしつつ、完了処理(`dispose`・`onComplete`)は`TICK_INTERVAL_MS * 2`(66ms)だけ遅らせてから呼ぶようにした。これにより`entry.crossfadingInstructionId`がセットされている間に`tick()`が最低1回は発火し、`crossfadeByWindow`に指示が乗るようになる。`TICK_INTERVAL_MS`は[src/shared.ts](../src/shared.ts)に定数として集約し、[src/tick-worker.ts](../src/tick-worker.ts)と[src/crossfade.ts](../src/crossfade.ts)の両方から参照するようにした(元々`tick-worker.ts`内にリテラルで持っていた値)。
  - 検証: `BroadcastChannel.prototype`ではなく実際に別の`BroadcastChannel`インスタンスで`norigvj-vj-state`を購読し、`crossfadeByWindow`を受信できた回数を計測する方法で、単一投影窓25回・複数投影窓(Randomボタン、2投影窓)15回のいずれも、修正前は0回、修正後は毎回複数回受信できることを確認した([src/crossfade.ts](../src/crossfade.ts)の`startCrossfade()`参照)。
